## 文档目的

本文档回答三个问题：**测什么、在哪一层测、达到什么标准算通过**。

- 把验收标准 AC-01~26 逐条映射到可执行的验证方式（单元 / 组件 / 集成 / E2E / 人工 / 上线验收），使每条 AC 都有明确的负责人可执行的检查点。AC-01~23 来自 PRD §14；AC-24~26 为 2026-08 后端改版的实现期续编（PRD 外扩展：管理员邮箱认证、内容推文 posts、公开 Outcome）。
- 定义 V1 的测试金字塔、测试数据 fixture 策略与回归集，作为 M0~M5 各阶段退出条件的验证依据。
- 作为 GitHub Actions CI 与本地验证的策略基线；实际命令和 workflow 以当前 `package.json`、`.github/workflows/` 为准。

读者假设：读者未读过 PRD。本文自含实现测试所需的全部前提、术语与契约；PRD 原文仅作为需求基线引用，不整段复制。

## 适用范围

- 适用对象：V1（M0~M5）全部交付物 —— 参与者 Web、管理员 Web、超级管理 Web（React 18 + Vite + TypeScript，手机优先）、PocketBase 服务端（认证、业务 hooks、权限规则、迁移）、SQLite schema 与迁移、规范化 ZIP/CSV 导出、备份与告警、Docker 部署。
- 适用阶段：现有 V1 回归与 2026-08-27 专项升级；仓库、Vitest、PocketBase 集成测试、Playwright 与 GitHub Actions 均已存在。
- 关键术语（与 PRD 一致）：
  - **三级账号**：超级管理员（全平台唯一）、管理员（绑定 `organization_id`）、参与者（全平台通用，不绑定机构）。
  - **活动内角色**：`activity_role` ∈ {倾诉者， 聆听者}，挂在报名记录上而非账号上。
  - **硬名额**：`capacity_total` / `capacity_speaker` / `capacity_listener`，审核通过须在服务端事务内校验。
  - **有效签到**：实际参与人数唯一口径；同一参与者同一活动仅一条。
  - **普通/敏感导出**：按字段与题目的 `is_sensitive` 标记过滤，不依赖字段名。

## 实现指引

### 1. 测试金字塔总览

原则：**业务规则的正确性以服务端集成测试为最终裁判**。前端隐藏按钮不是权限控制（PRD §11.2「前端不得成为唯一权限控制」），因此权限、名额、状态机、幂等等规则必须且只允许在服务端层断言；前端测试只覆盖渲染、交互与客户端校验体验。

| 层级 | 工具（约定） | 验证对象 | 数量占比（建议） | 特点 |
| --- | --- | --- | --- | --- |
| L1 单元测试 | Vitest | 纯函数：用户名规则、状态迁移矩阵判定、名额校验决策、指标口径计算、`is_sensitive` 导出过滤、CSV 序列化 | 多 | 毫秒级，无 IO |
| L2 组件测试 | Vitest + Testing Library | 表单渲染与校验提示、状态只读展示、按角色的 UI 差异 | 中 | jsdom，不起后端 |
| L3 服务端集成测试 | 起真实 PocketBase 测试实例，HTTP/SDK 断言 | 全部业务规则：名额事务、并发审核、状态迁移、签到唯一、幂等、限流、越权、审计、导出内容 | 多（核心） | 真实 SQLite + 迁移 + fixture |
| L4 E2E | 建议 Playwright（待确认） | 核心链路与关键权限场景的浏览器贯通 | 少 | 移动端 viewport |
| L5 人工 / 上线验收 | 人工 checklist | 兼容性、性能、备份恢复演练、部署冒烟 | 按发布 | 真机与真实环境 |

建议（非强制门槛，待确认）：状态迁移矩阵、名额/并发校验、导出过滤、指标口径四类核心逻辑追求高分支覆盖；全局不设统一百分比门槛，避免催生低价值测试。

### 4. 越权访问自动化测试套件（AC-03，CI 必过）

这是 PRD 点名要求自动化（「主要列表、详情与导出接口的自动化越权测试全部通过」）且风险最高（跨租户数据泄露）的套件，**独立成组、任何改动都全量运行**。

方法：以机构 A 管理员凭据，对机构 B 的资源发起全部主要接口请求，攻击向量包括：直接资源 ID、列表筛选参数、URL 路径参数、导出 `scope_json` 中伪造 `organization_id`、看板下钻参数。断言：跨机构资源与不存在资源统一返回 `404 not_found`，且响应体不含机构 B 任何数据；同时验证服务端忽略客户端伪造的机构参数（PRD §12.2）。无具体资源可隐藏的角色级端点拒绝仍可使用 403。

| 资源 | 列表 | 详情 | 导出/聚合 | 备注 |
| --- | --- | --- | --- | --- |
| activities | ✓ | ✓ | ✓（导出 scope） | 含已下架/已归档 |
| registrations / registration_answers | ✓ | ✓ | ✓ | 含审核操作接口 |
| checkins / checkin_sessions | ✓ | ✓ | ✓ | 含补签/撤销 |
| trainings / training_checkin_sessions / training_attendances | ✓ | ✓ | — | 含发布/关闭、签到开放/补签/撤销端点；培训签到资格为账号级全平台通用，补签候选人名单按设计即全平台 approved 聆听者去重（非越权） |
| activity_surveys / survey_questions | ✓ | ✓ | — | |

### 5. E2E 核心链路

主链路（对应 V1 端到端成功定义，PRD §1.3），在 360px 移动端 viewport 下运行：

```
未登录打开活动详情链接
  → 点击「立即报名」→ 输入新用户名+密码（自动注册并登录）
  → 选择角色、填写报名表、提交（看到保存凭据的回访指引）
  → 管理员登录后台审核通过
  → 管理员开放签到 → 参与者扫固定二维码签到成功（重复扫码提示已签到）
  → 管理员开放问卷 → 参与者从「我的」中心进入，保存草稿后继续，正式提交
  → 参与者只读查看本人已提交答案
  → 管理员发起普通导出 → 下载 ZIP，断言其中包含该报名/签到/答卷记录且敏感字段已过滤
```

辅助 E2E 场景（每个 1 条）：AC-04 发布审核双路径（开关开/关）；AC-05 未登录可见详情但报名被引向登录；AC-07 误判回退全流程（含原因与审计可见）；AC-17 敏感导出二次确认；AC-22 通用登录页登录后回跳原目标页且登录页无注册入口。

培训链路（2026-08 扩展，`e2e/tests/training-flow.spec.ts`，2 条）：正向——管理端列表 → 详情开放签到 → 聆听者扫码签到成功 → 幂等重扫 → 培训页显示「已通过」+「已完成聆听者培训」标记 → 管理端名单可见 → 撤销后培训页恢复「未参加」；负向——无 approved 聆听者报名者访问签到链接显示引导文案、/trainings 空态不泄露培训信息。

工具建议 Playwright（移动端 viewport 模拟、WebKit 内核近似 Safari；最终选型待确认）。E2E 数量刻意保持少而精，规则细节一律下沉到 L3。

### 10. 测试未覆盖的风险（明示）

- **SQLite 规模瓶颈**：fixture 为中小数据量，未验证 PRD §16.1 所述「SQLite 单点增长」拐点；大数据量下导出耗时与内存无保障。
- **真实微信内置浏览器怪异行为**：自动化仅模拟 viewport 与 UA，真机兼容靠人工抽查，覆盖不全。
- **真实备份链路**：CI 只模拟备份失败验证告警与审计；真实每日备份、异地存放、30 天保留的正确性只能上线验收确认。
- **部署与网络层**：域名、TLS、反向代理、Docker 卷隔离不在 CI 覆盖内，依赖 M5 冒烟 checklist。
- **限流/幂等的对抗性场景**：仅按约定阈值测试，未做安全级暴力破解模拟。
- **审计不可篡改的强度**：断言「无产品界面/API 途径修改」，不排除直接操作数据库的可能（属运维边界）。
- **并发压测深度**：并发审核/签到以「两请求竞争」验证逻辑正确性，未做高并发压力验证。
- **时区边界**：CSV 时间带时区已断言，跨时区展示靠人工核查。

## 验收标准

测试体系本身的验收（本文档的 DoD）：

1. AC-01~26 每条在 §6 映射表中都有主验证层级，且标注「集/E2E」的条目在 CI 中有对应自动化测试，禁止只留人工验证（AC-01、AC-19 除外，二者本质为上线验收）。
2. PR 合并门禁生效：lint、typecheck、unit、integration（含独立越权 job）、build、迁移校验全绿方可合并。
3. 越权套件覆盖 §4 接口清单，且存在「新增接口必须同步补充越权测试」的强制机制。
4. fixture 满足 §7 最小集合，且看板/导出类测试的期望值可手工从 fixture 推算。
5. 主链路 E2E 在 360px viewport 下贯通「详情→自动注册→报名→审核→签到→问卷→导出」。
6. M5 冻结前：全部 AC 按映射表执行完毕并记录结果；AC-19 恢复演练与 AC-23 真实备份告警在测试/生产环境实测通过；§9 人工核查 checklist 全部签字确认。

阶段关联：M0 退出条件中「隔离测试通过」即越权套件首版；M2 退出需名额/签到/幂等套件；M3 需问卷与模板版本套件；M4 需看板口径与导出规范套件；M5 需全量回归 + 上线验收。
