## 1. 背景与目标

现有网站已经具备活动创建、报名审核、签到、问卷、看板和固定 ZIP/CSV 导出，但参与者仍使用用户名和密码，现场没有倾诉者/聆听者配对，机构后台也缺少围绕单场活动的实时工作台。本次升级把重点从“功能能走通”推进到“机构能高效办完一场活动”。

目标包括：

1. 参与者账号改为绑定并验证中国大陆手机号，手机号成为主要登录身份；报名时必填姓名，用于审核和现场找人。
2. 优化机构从创建活动、招募审核、现场执行到活动后复盘导出的完整流程。
3. 增加单场活动实时工作台，集中展示报名、审核、签到、配对和问卷完成情况。
4. 按现场有效签到顺序为倾诉者和聆听者编号、配对，并在参与者端实时展示本人编号和搭档。
5. 将导出从固定整包升级为可选择活动、问卷、参与者、行筛选条件和字段列的导出向导。

成功标准：机构管理员不用在活动详情、签到、问卷、表格之间反复切换，就能完成一场活动；参与者签到后能清楚知道自己的编号、配对状态和搭档；所有涉及个人信息的读取和导出均遵守最小权限、显式选择和审计规则。

## 2. 已确认的产品决策

| 主题 | 决策 |
| --- | --- |
| 参与者身份 | 不再以“匿名用户名账号”为目标；使用已验证手机号作为主要账号身份。第一阶段只支持中国大陆 `+86` 手机号。 |
| 登录方式 | 新账号使用阿里云短信认证验证码登录/注册，不再要求创建用户名。已登录会话仍可保持，具体有效期沿用现有会话策略。 |
| 存量账号迁移 | 存量用户先以原用户名和密码登录，再完成手机号验证码绑定；绑定成功后保留原 `participant_id` 和历史记录，手机号成为后续主要登录身份。不得通过“创建新账号”迁移历史数据。 |
| 姓名 | 姓名是每次活动报名的必填标准字段，用于审核、现场找人和向本人搭档展示；不进入普通分析指标。账号层不强制保存姓名，避免跨活动错误复用。 |
| 短信服务 | 当前使用阿里云“短信认证”快速接入，仅发送登录、注册、绑定手机号所需验证码；暂不办理普通短信签名与模板资质。 |
| 活动通知 | 本阶段不发送活动通知短信。活动审核结果、时间地点变化和现场安排优先通过站内状态与微信群通知。普通活动通知短信待主体资质、短信签名和模板审核完成后再启用。 |
| 实时能力 | 管理后台单场活动工作台和参与者配对状态使用 PocketBase Realtime/SSE；断线后自动重连，并以重新拉取快照纠正漏事件。 |
| 参与者结构 | 后台可以展示年龄段、性别、活动角色、新老参与者、到场情况、报名提前量等聚合结构；不展示基于情绪、心理或问卷敏感回答生成的个体画像。 |
| 配对规则 | 按有效签到顺序分别给倾诉者和聆听者编号；管理员点击“开始配对”后，第一位倾诉者配第一位聆听者，依次类推。已形成的配对不会因迟到者自动重排。 |
| 导出 | 默认输出 XLSX；高级用户可导出规范化 CSV ZIP。支持单活动、单问卷、指定参与者、行筛选、字段列选择和题目选择。 |

### 2.1 外部服务边界

- 阿里云“短信认证”支持个人或企业实名认证账号，使用平台预设签名和模板，不要求本阶段自行提交企业资质、短信签名和短信模板；它只适合验证码，不等于普通短信发送能力。实现前仍需在实际阿里云账号控制台确认开通资格、价格和可用地区。官方资料：[短信认证新手指南](https://help.aliyun.com/zh/pnvs/getting-started/sms-authentication-service-novice-guide)、[短信认证服务说明](https://help.aliyun.com/zh/pnvs/user-guide/sms-authentication-service)。
- 短信认证按每条验证码的实际用途选择模板：登录/注册用登录/注册模板，首次绑定与换绑新号用绑定新手机号模板，换绑时验证当前旧号用验证绑定手机号模板；模板 CODE 为阿里云控制台赠送模板的固定实现常量（详见 [production-readiness-batch-1-plan.md](production-readiness-batch-1-plan.md) §4.1）。
- 活动提醒属于普通通知短信，不能复用短信认证接口。后续若启用，须走普通短信产品的签名、模板与资质流程；不得发送微信群邀请、加群诱导或营销信息。官方资料：[通知短信模板规范](https://help.aliyun.com/zh/sms/user-guide/notification-template-specifications)。
- PocketBase Realtime 基于 SSE，作为实时看板与本人配对状态的推送机制；数据库仍是最终事实来源。官方资料：[PocketBase Realtime API](https://pocketbase.io/docs/api-realtime/)。

## 3. 参与者账号与报名流程

### 3.1 新用户

1. 用户点击报名或登录。
2. 输入手机号，勾选隐私说明和必要通知说明。
3. 获取并输入验证码；服务端验证成功后，以规范化手机号查找账号。
4. 账号不存在则创建 `participant_accounts`，存在则直接登录；任何重试不得创建重复账号。
5. 进入活动报名，选择倾诉者/聆听者角色，填写姓名和活动配置的其他字段。
6. 报名成功后进入“我的活动”，查看审核状态、签到入口、配对状态和问卷任务。

### 3.2 存量用户名账号

1. 保留“原账号迁移”入口，要求用户名和密码登录；仅允许登录迁移前已存在的账号，未知用户名与错误密码返回同形错误，绝不创建账号或签发 token。
2. 登录成功后要求输入手机号并完成验证码验证。
3. 若手机号未被占用，将手机号绑定到当前 `participant_id`；若已绑定其他账号，停止自动处理并进入人工账号合并流程，不能覆盖或静默迁移。
4. 绑定成功后，历史报名、签到、培训和问卷数据仍关联原 `participant_id`。
5. 迁移稳定后再评估是否下线用户名登录；本次不硬删除 `username` 字段。

### 3.3 账号异常与安全状态

- 验证码获取需同时限制手机号、来源 IP、设备会话和单位时间次数；接口响应不得泄露手机号是否已注册。
- 验证码短时有效、一次性使用；服务端不记录验证码明文。
- 换绑手机号必须在已登录状态下再次验证新手机号；必要时同时验证旧手机号。无法接收旧号时走人工支持，不提供低门槛绕过。
- 账号被停用时，即使验证码正确也不能登录。

## 4. 机构活动全流程

### 4.1 创建与发布

活动创建由长表单改为分步向导：

1. 基本信息：标题、介绍、时间、地点、总名额。
2. 角色与报名：倾诉者/聆听者名额、报名时间、姓名等标准字段、角色专属字段。
3. 现场设置：固定二维码签到、预计签到开放时间、是否启用现场配对。预计时间仅作运营提示，不自动开放；配对首次开始后不能再改变开关。
4. 问卷：从模板添加活动前、现场或活动后问卷，保存 `phase=before/onsite/after`、适用角色和预计开放时间；实际开放/结束继续按管理员手动操作。
5. 预览与发布：同时预览参与者端活动详情和报名表，展示缺失项与下一步。

支持“复制上一场活动”和机构活动模板。模板用 `activities.is_template=true` 的私有草稿保存，不能直接发布；列表可另存模板，创建入口可从本机构模板生成独立普通草稿。复制重新生成活动代码、签到 token、问卷 token，清空签到/问卷预计开放时间，保留角色设置和问卷阶段，不复制人员历史。活动时间和报名窗口复制后仍须人工调整。

### 4.2 招募与审核

活动详情页按生命周期展示下一步操作，而不是只有平铺标签页：

- 招募中：报名趋势、待审核数、角色名额、批量审核、联系名单导出。
- 活动前：已通过人数、预计到场、缺少必填资料、微信群通知文案、现场准备检查清单。
- 现场中：签到、配对、问卷完成、异常处理统一进入“现场工作台”。
- 活动后：问卷催办、数据质量检查、导出、复盘摘要和归档。

### 4.3 现场工作台

单场活动默认展示：

| 区域 | 指标或操作 |
| --- | --- |
| 报名漏斗 | 报名总数、待审核、已通过、已拒绝、已取消；按倾诉者/聆听者拆分 |
| 签到 | 已通过人数、有效签到人数、签到率、最近签到列表、手工补签/撤销 |
| 配对 | 两类角色已签到数、已配对组数、等待人数、未平衡差额、开始配对、手工调整 |
| 问卷 | 每份问卷的符合资格人数、已提交人数、现场完成率、总体完成率、未完成人数 |
| 参与者结构 | 年龄段、性别、角色、新老参与者、历史活动参与次数、报名提前量等聚合图表 |
| 快捷动作 | 开放/关闭签到、开始配对、开放/结束问卷、复制通知文案、导出当前视图 |

实时口径：

- `现场问卷完成率 = 当前仍为有效签到且角色符合的有效已提交人数 ÷ 当前有效签到且角色符合人数`，用于现场追踪。分子必须与当前分母人群取交集；提交后被撤销签到者不得继续留在分子中。
- `总体问卷完成率 = 当前仍为已审核通过且角色符合的有效已提交人数 ÷ 当前已通过且角色符合人数`，用于活动后复盘，并保留现有指标口径。分子同样与当前分母人群取交集；提交后报名不再是 approved 的参与者不得继续留在分子中。
- “有效已提交”仅指 `submission.status=submitted` 且未作废的答卷，并按参与者去重。任一分母为 0 时显示“—/暂无符合资格参与者”，不显示 `0%`；两个完成率均不得超过 100%。
- 所有卡片显示“最后更新时间”；Realtime 断开时显示离线状态，恢复后重新请求整页快照。
- 聚合分组人数少于 5 时不展示细分值，合并为“样本不足”，降低小群体被反推身份的风险。

## 5. 现场编号与配对

### 5.1 编号

- 有效签到成功后立即按角色分配不可变的现场序号：倾诉者 `S01, S02...`，聆听者 `L01, L02...`。
- 在线签到以数据库事务实际成功分配现场号的顺序递增编号；该顺序与对应角色计数器的原子自增顺序一致，不声称用客户端时间或预生成 ID 决定并发先后。存量签到不补发现场号。
- 编号只在单场活动内唯一。撤销签到不复用已经发出的编号，以免现场口头编号发生变化。

### 5.2 配对

1. 管理员确认现场基本到齐后点击“开始配对”。
2. 服务端在事务内分别读取尚未配对的有效倾诉者与聆听者队列，按现场序号升序逐一配对。
3. 第 `n` 位待配对倾诉者与第 `n` 位待配对聆听者组成一组，分配 `P01, P02...`。
4. 配对开始后迟到者继续取得自己的现场序号；当两边都存在等待者时，按队首自动补成新组。
5. 已形成的配对不因迟到者、刷新或重复调用而重排；重复“开始配对”是幂等操作。
6. 签到撤销：活动开始前可释放该参与者的配对并把仍有效的搭档放回等待队列；活动开始后只允许管理员手工调整，必须填写原因并写审计。
7. 手工调整必须事务化，保证同一参与者同一时刻至多属于一个有效配对。

### 5.3 参与者端展示

参与者只能查看本人所在活动的本人配对信息，不能枚举其他组。搭档手机号不展示。

| 状态 | 参与者看到的内容 |
| --- | --- |
| 已签到，配对未开始 | 本人现场编号；提示等待工作人员开始配对 |
| 配对已开始，对侧暂无人 | 本人现场编号；提示正在等待搭档 |
| 已配对 | 配对组号、本人编号、搭档编号、搭档本次报名姓名 |
| 已调整 | 新配对组号和新搭档；明确提示安排已更新 |
| 签到已撤销 | 配对信息不可用；提示联系现场工作人员 |

展示入口：签到成功页、“我的活动”卡片、活动现场页。三处使用同一 API 与实时事件，不各自推导配对结果。

移动端以“我的现场编号”卡片作为主入口；参与者点开卡片后查看组号和搭档信息。等待、已配对和已调整使用文字与状态图标共同表达，不能只依赖颜色。

## 6. 数据看板与参与者结构

后台用“参与者结构”而不是“用户画像”命名，明确只做运营所需的群体统计。

可直接从报名、签到和历史参与记录聚合的内容：

- 年龄段、性别、活动角色占比；
- 新参与者/回访参与者占比；
- 报名到活动开始的提前天数；
- 审核通过率、签到率、爽约率；
- 历史参加活动次数分布：按本机构其他活动 `valid` 签到逐人逐场去重，截止本场开始与当前快照较早时间，不含本场、撤销签到或只有报名的记录；0 次为新参与者；
- 聆听者培训通过比例；
- 每份问卷的现场完成率和总体完成率。

边界：

- 姓名、手机号不作为维度，不进入普通图表或公开报告。
- 不把问卷中的心理、情绪、健康或其他敏感回答与姓名、手机号合并生成个人标签。
- 管理员查看结构图时仍受本机构和单活动范围限制；跨机构历史只用于平台级去标识化累计口径，除非另有明确授权。
- 年龄优先存为年龄段或出生年份，不默认收集完整出生日期；具体标准字段在实现前冻结。

## 7. 细粒度导出

导出页改为五步向导：

1. 范围：平台、机构、单场活动、日期范围或指定参与者。
2. 数据域：报名、签到、配对、单份/多份问卷、完整活动复盘。
3. 行筛选：角色、报名状态、是否签到、是否已配对、问卷是否完成、指定参与者。
4. 字段：系统 ID、姓名、掩码/完整手机号、角色、审核、签到、现场编号、配对、性别、年龄/年龄段、自定义报名字段、问卷和具体题目。
5. 格式：XLSX（默认，面向机构日常使用）或规范化 CSV ZIP（高级分析）。

预设模板：联系名单、签到名单、现场配对表、参与者结构数据、单份问卷结果、活动完整复盘、指定参与者资料。

字段选择与权限规则：

- “指定参与者”是行筛选；“性别、年龄、姓名、手机号”等是列选择，两者可以组合。
- 只要所选内容包含任一 `registration_field_defs.is_sensitive=true` 的报名字段、任一 `survey_questions.is_sensitive=true` 的问卷题目，或账号层定义为敏感的完整手机号等字段，任务就自动升级为敏感导出。姓名、微信号和自定义联系方式只是示例，不能靠字段名枚举判断。敏感导出要求机构开关已开启、操作者二次确认并写审计。
- 敏感性由服务端根据字段/题目定义和账号字段策略计算；`POST /api/cc/exports/preview` 与正式导出必须使用同一判定函数。前端只能展示服务端返回的 `requires_sensitive_export` 和原因，不能作为唯一门槛。
- 审计至少记录操作者、机构、活动、参与者筛选、字段代码、问卷/题目代码、文件格式和时间；审计 metadata 不写实际答案或完整手机号。
- 普通分析预设默认不包含姓名和手机号；手机号若仅为现场联系，可提供掩码列。
- 导出结果必须带筛选摘要、字段字典、生成时间和时区，确保后续可复现。

## 8. 隐私文案

账号绑定和报名页使用以下主文案：

> 我们仅将你的姓名和手机号用于账号验证、活动报名、审核、现场联系、签到和必要的活动安排，不用于广告营销、商业画像或出售给第三方。统计分析仅使用去标识化数据，不展示姓名和手机号；未经另行同意，我们不会将联系方式与问卷中的敏感回答用于个体分析。

必要通知另设单独勾选或说明，不与营销同意合并：

> 接收本次活动的必要通知，包括审核结果、时间地点变更和现场安排。该选择不代表同意接收营销信息。

完整政策入口 `/privacy` 已实现；主体、邮箱、备案与保留期限按用户确认值落实，见 [隐私运营手册](../privacy-operations.md)。可关联个人的活动/培训记录保留至结束后 2 年，账号资料至注销处理完成，备份滚动 30 天；到期及隐私请求由运营处置，未实现自动业务清理。个人信息处理以适用法规及具体事项审查为准。

## 9. 目标数据与 API 契约

T0 已将目标契约冻结为 `2026-08-28.t0-v1`。机器名与共享 TypeScript 类型以 `frontend/src/shared/api/accountEvent.ts` 为准，权限、请求/响应、Realtime 和 v1 兼容语义见 [api-design.md](api-design.md)，数据库约束与迁移顺序见 [database-design.md](database-design.md) 「6. T0 冻结契约」。未来改机器名必须走契约版本变更，不得在并行任务内自行微调。

### 9.1 数据变更

- `participant_accounts`：追加 `phone_e164`、`phone_lookup_hash`、`phone_verified_at`、`phone_binding_source`、`phone_migration_status`。精确查找/唯一索引使用带部署 secret 的 HMAC-SHA256 hash。PocketBase 0.28.4 已实测可将 text 手机号加入 password identity，但因产品只提供短信验证码，T0 决定不这样做；验证成功后由 hook 签发 token，username identity 仅保留给存量迁移。
- `registration_field_defs`：冻结 `FULL_NAME`(text，必填，敏感，只用于联系/配对)、`GENDER`(single_choice，选填，仅聚合)、`AGE_RANGE`(single_choice，选填，仅聚合)。不收集 `BIRTH_YEAR` 或完整生日；任一聚合分组低于 5 人时，同维度全部分组一起抑制，避免通过总数和互补桶反推。
- `activities`：追加 `pairing_started_at/by` 与 `onsite_locked_at/by`，分别作为迟到自动补配和活动开始后高风险调整的服务端事实。
- `checkins`：追加 `onsite_role`、`onsite_sequence`、`numbered_at`；号码发出后即使撤销签到也不复用。
- 新增 `activity_pairs`：活动、`pair_sequence`、双方 registration/checkin、状态 `active/released/completed`、配对/释放/完成时间、操作者与原因；同一参与者每场活动至多一个 active 配对。
- `export_jobs.scope_json`：冻结 `schema_version:2` 的范围、数据域、问卷、参与者/行筛选、系统列、报名字段、问卷题目、格式与时区。旧 `{scope, include_pii, confirm}` 请求由服务端归一化为 v2 后执行，至少保留一个发布窗口。

### 9.2 端点建议

| 端点 | 作用 |
| --- | --- |
| `POST /api/cc/auth/participant/request-code` | 请求手机号验证码；防枚举、限流 |
| `POST /api/cc/auth/participant/verify-code` | 验证并登录/注册手机号账号 |
| `POST /api/cc/auth/participant/bind-phone` | 存量用户名账号绑定已验证手机号 |

| `POST /api/cc/activities/:activityId/pairings/start` | 幂等批量配对 |

## 11. 验收清单

- 手机号验证码登录/注册幂等；同一手机号不能生成多个账号；存量绑定保留原 `participant_id` 和全部历史记录。
- 姓名在每场报名中必填，但普通看板、普通分析导出和公开报告不包含姓名或手机号。
- 实时工作台的报名、有效签到、配对、问卷指标与底层记录、导出结果一致；断线重连后能自校正。提交后撤销签到只从现场完成率的分子和分母同时移除，提交后取消/回退报名只从总体完成率的分子和分母同时移除；两个比率不得超过 100%，分母为 0 时显示“—”。
- 相同签到数据无论重复执行多少次“开始配对”，配对结果都一致；并发签到和并发配对不产生一人多配或重复组号。
- 参与者只能读取自己的编号和搭档；无法通过改 URL、活动 ID 或订阅条件枚举他人配对。
- 撤销签到、释放配对、手工调整均遵守活动开始前后规则并写审计。
- 单份问卷导出只包含所选问卷；指定参与者导出只包含授权范围内所选人员；字段选择严格生效。
- 选择任一 `is_sensitive=true` 的标准/自定义报名字段或问卷题目，以及账号层敏感字段时，服务端均自动触发敏感导出门槛、二次确认和审计；至少用一个自定义敏感字段（如微信号）验证不能绕过。
- 360px 移动端和微信内置浏览器能完成验证码登录、报名、签到、查看配对和填问卷。
- 阿里云不可用或验证码发送失败时给出可重试状态，不创建半成品账号；密钥仅由环境变量或部署 secret 注入。

## 13. 非目标

- 本期不发送营销短信，不用短信认证接口发送活动提醒或微信群邀请。
- 本期不基于心理、情绪、健康或问卷敏感答案生成个体画像、评分或自动决策。
- 本期不让参与者查看全场配对名单、搭档手机号或其他参与者报名资料。
- 本期不因手机号升级重写或删除历史 `participant_id`。
- 本期不把 XLSX 作为唯一机器分析格式；规范化 CSV ZIP 继续保留。
- 本期不自动把活动消息发送到微信；只提供可复制的群通知文案。
